# Agent Search Alert Hardening Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make agent-native search-alert preparation and decisions atomic, retry-safe, review-bound, and retention-safe without adding a Jobbbler UI decision surface.

> **Status:** This initial defect-by-defect plan is retained as RED-test provenance. The production implementation and final interfaces are defined by `2026-08-30-agent-search-alert-durable-saga.md` and its linked design; those documents supersede any narrower interface or cleanup wording below.

**Architecture:** A required client-generated `Idempotency-Key` claims request preparation before any saved-search or verification side effect. A separate exact-decision claim serializes approval and decline before challenge consumption or scheduling; purpose-bound email-verification lifecycle methods preserve shared verified endpoints, clean declined/failed reviews, and let the worker purge unattended expired review data. SQLite and PostgreSQL implement the same identity and idempotency repository contracts, with PostgreSQL using one atomic insert-on-conflict statement.

**Tech Stack:** TypeScript 6, Zod 4, Vitest 4, Next.js route handlers, SQLite/better-sqlite3, PostgreSQL/postgres.js, existing recurring worker.

**Spec:** `docs/superpowers/specs/2026-08-30-agent-native-alert-activation-design.md`, refined by the verified defects from commit `b18cb02` and the product invariants supplied on 2026-08-30.

## Global Constraints

- The external agent client presents the exact decision; Jobbbler stores bound evidence and never infers approval.
- No site click or new UI is added.
- Approval requires and validates the exact review-bound six-digit challenge.
- Decline requires no mailbox code and consumes no mailbox challenge.
- A search-alert review must never downgrade or rewrite a previously verified shared endpoint.
- Declined, failed, expired, and unattended review-scoped provisional email data is removed; verified endpoints and unrelated identity/recovery challenges are preserved.
- `Idempotency-Key` is generated by the external client/provider, not by the model.
- Existing dirty files owned by other workers are not edited until their changes are committed and the files are clean.
