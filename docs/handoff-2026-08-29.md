## What shipped in this pass

**Public portal.** Typography-first registry redesign: hero search (role + location) on the
landing page only, latest roles beneath it, a left filter rail (searchable multi-selects for
function and seniority, salary slider with currency, work-model chips, date-posted select,
exclusions), instant filter application, and a role page that reads like an article with
server-side first paint (`apps/web/src/app/jobs/[jobId]/page.tsx` passes `initialResult` into the
client view). Light/dark themes persist; reduced motion disables all animation.

**Global Agent layer (the judge-facing layer).** A persistent, horizontally resizable side panel
available on every page that shifts content instead of overlaying it. Its status distinguishes
the six stable site-wide core tools from contextual tools available on the current page. Three
tabs, in order:

- _Guide_ — "Try it in 10 seconds", suggested workflows derived from the planner data, and a
  note that agents can fetch the same plans via `plan_job_workflow`.
- _Activity_ — two-level entries: a human sentence first, then `tool_name · status · duration`.
  States are Complete (green), Needs user (amber), Error (red), Cancelled.
- _Tools_ — all 24 focused tools, grouped by the product area they operate on. The same set stays
  discoverable across navigation; private and stage-specific tools validate readiness when called.

The panel auto-opens Activity when tool calls arrive and respects a user's manual tab choice.
One deliberate motion accent — the "agent pulse" sweep across the results heading when an agent
updates the page — is the only decoration; no gradients, no kickers.

**WebMCP surface.**

- All 24 tools are registered on every route. Six clear entry tools are
  `plan_job_workflow`, `get_search_filters`, `search_jobs`, `open_job_details`,
  `prepare_application`, and `open_jobbbler_page`. `plan_job_workflow` is a goal-oriented advisory manifest (five
  goals in `apps/web/src/features/webmcp-workflows.ts`) that tells an agent which tools compose
  an outcome, which steps stay with the human, and the boundaries. It executes nothing, grants
  nothing, confirms nothing.
- Navigation tools — `open_job_details`, `open_saved_search`, `add_job_to_comparison` — let an
  agent traverse the whole site without human clicks. The tool set remains stable across routes.
- `get_latest_search_update` reports only the delta since a saved search's last run ("Since the
  last check: 3 new, 1 updated, 0 closed…") with a bounded change list.
- `get_search_filters` returns the exact accepted filter vocabulary — categories, work models,
  seniorities, salary options, sort orders — derived from the Zod contracts, so agents never
  guess enum values.
- `get_search_state` includes an explicit truncation summary for bounded criteria: complete,
  omitted values, and shortened values.
- `get_job_application_capability` answers "how does this role accept applications?" before a
  workflow starts: what an agent may prepare, which steps stay human, whether an external
  handoff is required, and honestly reports that retraction and status sync from an external
  employer system are unavailable after handoff.
- Every tool carries a humanized `title`, honest `readOnlyHint`/`untrustedContentHint`
  annotations, and Zod validation errors come back as bounded self-correction hints (up to three
  field-level messages) so agents can retry without guessing.
- `apps/web/src/lib/webmcp-catalog.ts` is the canonical catalog; a sync test keeps it, the eval
  fixtures, and the registered sets consistent in both directions.
- A manifest-validation test (`apps/web/src/features/webmcp-manifest-validation.test.ts`)
  validates every route's tool set and ten application-stage scenarios, so a name that breaks
  registration can never ship again.

**Alert lifecycle backend.** Idempotent saved-search creation (`Idempotency-Key`, 24 h TTL,
409 on body mismatch, race-safe), schedule PATCH with `expectedVersion`, and cascade DELETE.
Verified against both the SQLite and Postgres storage contract suites.

## Decisions worth knowing

- **Stable core plus contextual tools.** WebMCP is a document-level API, so every page registers
  the same six safe core tools and adds only the contextual tools that fit its route and state.
  Navigation and the planner make the full site reachable, while state-dependent registration
  remains a guardrail (consent tools only exist at the consent stage).
- **Imperative-only registration.** Recorded with rationale in
  `docs/architecture/webmcp-capability-matrix.md`.
- **Loginless trust model.** Anonymous owner + HttpOnly session, email OTP recovery, draft-bound
  expiring delegations, payload-bound consent grants, five-minute single-use confirmations, and
  an honest `handed_off` terminal state. See
  `docs/architecture/agent-authorization-and-consent.md`.
- **One motion accent, no decoration.** Gradients, AI spheres, robots, avatars, in-site chat, and
  decorative dashboard metrics were all considered and rejected; the agent pulse is the single
  branded moment, and it is disabled under reduced motion.

## Environment notes

- The dev server does not read the root `.env`. Start it with the variables exported:

  ```
  export NOTIFICATION_DRIVER=capture ALLOW_LOCAL_OTP_CAPTURE=true \
    PUBLIC_BASE_URL=http://localhost:3000 JOBBBLER_WORKER_MODE=idle \
    SQLITE_DATABASE_PATH="$(pwd)/.data/jobbbler.sqlite"
  pnpm --filter @jobbbler/web dev
  ```

- A stale dev server blocks both `next dev` and Playwright. Clear it with
  `pkill -f next-server; pkill -f "next dev"; rm -rf apps/web/.next/dev`.
- `.impeccable/` is a local editor-tooling cache. It is now ignored and untracked, but it still
  exists inside four earlier commits on this branch. If a fully clean history is wanted before
  the repo goes public, rewrite the unpublished branch first:

  ```
  FILTER_BRANCH_SQUELCH_WARNING=1 git filter-branch -f \
    --index-filter "git rm -r --cached --ignore-unmatch --quiet .impeccable" -- 1936210..HEAD
  ```

  This is optional; nothing references the file.
